# PostgreSQL

> 유연하고 표준에 충실한 오픈소스 관계형 데이터베이스

## Oracle DB vs. PostgreSQL
Oracle에 비해 PostgreSQL은 상당히 친숙하면서도 '가성비'와 '자유도'가 높다고 볼 수 있음.

* _표준 준수 및 기능성_: PostgreSQL은 SQL 표준(ANSI-SQL)을 가장 엄격하게 따르는 DB 중 하나입니다. Oracle에서 제공하는 복잡한 Stored Procedure(PL/pgSQL), Window Functions, CTE(With문) 등을 거의 동일하게 지원합니다.

* _비용 및 라이선스_: Oracle은 막대한 라이선스 비용이 들지만, PostgreSQL은 완전 무료 오픈소스(PostgreSQL License)입니다. 상용 수준의 성능을 내면서도 비용 부담이 없어 많은 기업용 솔루션(GitLab 등)의 백엔드로 채택됩니다.

* _확장성(Extensibility)_: PostgreSQL의 별명이 "객체-관계형(ORDBMS)"인 이유입니다. 단순 데이터 저장을 넘어 사용자가 새로운 데이터 타입, 인덱스 유형, 언어를 직접 정의해 넣을 수 있습니다.

## Redis vs. PostgreSQL
캐시로 Redis를 활용 중이시라면, PostgreSQL의 JSONB 지원 기능에 주목할 필요가 있음.

* _비정형 데이터 처리_: PostgreSQL은 JSONB라는 이진 JSON 타입을 지원합니다. Redis처럼 Key-Value 형태나 문서(Document) 지향 데이터를 인덱싱하고 쿼리할 수 있어, 경우에 따라 NoSQL의 역할까지 일부 수행합니다.

* _영속성 vs 속도_: Redis는 In-memory 기반으로 극강의 속도를 자랑하지만, PostgreSQL은 디스크 기반의 강력한 ACID 트랜잭션 보장이 우선입니다. GitLab에서 이슈 트래커나 사용자 설정 같은 중요 데이터를 안전하게 보관해야 할 때 PostgreSQL이 그 역할을 맡습니다.

## 왜 GitLab은 PostgreSQL을 쓸까?
GitLab이 예전에 MySQL에서 PostgreSQL로 완전히 전환한 결정적인 이유는 복잡한 관계 처리와 성능 때문임.

* _동시성 제어 (MVCC)_: PostgreSQL은 다중 버전 동시성 제어(MVCC) 능력이 매우 뛰어납니다. 수천 명의 개발자가 동시에 push하고 코멘트를 다는 GitLab 환경에서 읽기/쓰기 성능을 안정적으로 유지합니다.

* _고급 인덱싱_: GIN, GiST 같은 특수 인덱스를 지원하여 소스 코드 검색이나 로그 분석 같은 복잡한 검색 작업에 유리합니다.

* _신뢰성_: 데이터 무결성을 유지하는 기능이 매우 견고하여, 소스 코드 관리 시스템처럼 데이터 유실이 치명적인 서비스에 적합합니다.

## 개발자가 알아두면 좋은 점
이미 Oracle을 다루신다면 PostgreSQL 적응은 매우 쉬움.

* 대소문자 구분: Oracle은 기본적으로 식별자를 대문자로 처리하지만, PostgreSQL은 따옴표가 없으면 소문자로 처리합니다.

* 도구: Oracle의 SQL Developer 대신 pgAdmin 4나 DBeaver를 주로 사용합니다.

* 커뮤니티: 오픈소스 생태계가 워낙 커서 PostGIS(지리정보), TimescaleDB(시계열) 같은 확장 모듈을 붙여 Oracle보다 훨씬 다양한 용도로 변신시킬 수 있습니다.

### 결론
> 무겁고 비싼 Oracle을 대체하며 NoSQL의 유연함까지 챙긴 DB.

## Gemini와 일문 일답
1. Stored Procedure, Windows Function, CTE가 무슨 기능일까요 ?

    **SQL의 고급 기능들 (SP, Window Function, CTE)**

    이 기능들은 복잡한 데이터를 DB 안에서 효율적으로 처리하기 위해 사용합니다.

    Stored Procedure (저장 프로시저): 여러 개의 SQL 문을 하나의 함수처럼 묶어 DB에 저장해둔 것입니다. 네트워크 부하를 줄이고, 복잡한 로직을 DB 서버 안에서 직접 실행할 때 씁니다.

    Window Function (윈도우 함수): 행과 행 간의 관계를 계산할 때 씁니다. 예를 들어 "현재 행의 매출이 전체에서 몇 위인지(RANK)" 혹은 "직전 행과의 차이" 등을 낼 때 사용하며, OVER() 절이 특징입니다.

    CTE (Common Table Expression): 쿼리 내에서 임시로 사용할 수 있는 가상 테이블입니다. WITH 문으로 시작하며, 복잡한 서브쿼리를 가독성 있게 만들거나 재귀 쿼리를 짤 때 필수적입니다.

2. 새로운 데이터타입, 인덱스 유형, 언어를 직접 정의해 넣을 수 있다는게 무슨 말이죠 ?

    **PostgreSQL의 확장성 (Custom Definition)**
   
    일반적인 DB는 정해진 규칙만 써야 하지만, PostgreSQL은 마치 "플러그인"을 끼우듯 기능을 추가할 수 있습니다.

    데이터 타입: '지리 정보(위경도)', '복합 구조체' 등 세상에 없던 타입을 직접 만들 수 있습니다.

    인덱스 유형: 기본 B-Tree 외에도 데이터 특성에 맞는 검색 알고리즘을 개발자가 직접 구현해 넣을 수 있습니다.

    언어: DB 내부 로직을 짤 때 SQL뿐만 아니라 Python, JavaScript, Perl 같은 언어를 그대로 가져와 쓸 수 있습니다.

4. NoSQL은 뭔가요 ?

    **NoSQL이란? (Not Only SQL)**
    전통적인 표(Table) 형태의 RDBMS 틀을 벗어난 모든 DB를 통칭합니다.

    특징: 고정된 스키마가 없고 확장성이 뛰어납니다.

    예시: Redis(Key-Value), MongoDB(Document) 등.

    PostgreSQL과의 관계: PostgreSQL은 RDBMS지만 NoSQL처럼 JSON 데이터를 다루는 기능이 매우 강력해서 두 영역을 넘나듭니다.

5. 이슈트래커는 뭐죠 ?

   소프트웨어 개발 중 발생하는 버그, 개선 사항, 작업 단위(Task) 등을 기록하고 추적하는 시스템입니다. GitLab의 'Issues' 메뉴가 바로 그것이며, "누가, 언제, 무엇을 수정해야 하는지"를 관리하는 게시판의 확장판이라 보시면 됩니다.

6. 일반적으로 RDBMS가 신뢰성이 높은편이라고 볼 수 있나요 ?

   네, 일반적으로 RDBMS는 데이터 무결성 면에서 매우 신뢰성이 높습니다.

   ACID라는 원칙(원자성, 일관성, 고립성, 지속성)을 철저히 지키기 때문입니다. 예를 들어 "은행 이체"처럼 "내 계좌 출금"과 "상대 계좌 입금"이 동시에 완벽히 성공해야만 하는 작업에 최적화되어 있습니다.

7. 오라클은 대소문자 구분 없이 다 대문자로 인식한다는 얘기인가요 ?

   네, 정확히는 "사용자가 소문자로 써도 Oracle 내부적으로는 모두 대문자로 바꿔서 저장/인식"한다는 뜻입니다.

   Oracle: select * from users;라고 치면 내부적으로 USERS 테이블을 찾습니다.

   PostgreSQL: 반대로 모두 소문자로 인식합니다. 만약 대문자가 포함된 테이블을 만들고 싶다면 반드시 쌍따옴표("Users")를 써야 합니다. 이 차이 때문에 마이그레이션 시 쿼리 오류가 자주 발생하곤 합니다.

8. 이슈트래커가 커밋 로그랑은 다르죠 ? 커밋 내역도 postgreSQL에 저장되죠 ?

   결론부터 말씀드리면 이슈 트래커와 커밋 로그는 목적이 다르며, 저장되는 위치도 다릅니다.

   이 부분을 이해하면 GitLab이 왜 PostgreSQL과 Git(파일 시스템)을 동시에 사용하는지 명확해집니다.

   커밋 내역과 실제 소스 코드는 PostgreSQL에 저장되지 않습니다.

   Git의 원리: Git은 파일의 변경 이력을 파일 시스템(.git 폴더 내부)에 스냅샷 형태로 저장합니다. 텍스트 파일 기반의 효율적인 저장 방식을 사용하기 때문에 굳이 무거운 DB에 넣지 않습니다.

   GitLab의 역할: GitLab은 이 Git 파일들을 관리하기 위해 Gitaly라는 별도의 서비스를 사용합니다. 즉, 소스 코드는 서버의 하드 디스크에 파일 형태로 존재합니다.

   **그럼 PostgreSQL은 무엇을 저장하나요?**

   GitLab 내에서 "코드 그 자체"를 제외한 거의 모든 메타데이터를 저장합니다.

   사용자 정보 (아이디, 비밀번호, 권한)

   이슈(Issue)와 머지 리퀘스트(MR)의 제목, 내용, 댓글

   프로젝트 설정 값

   커밋의 "메타데이터": 커밋 해시 값, 누가 커밋했는지 등의 요약 정보는 빠른 검색을 위해 DB에 복사본을 저장해두기도 하지만, 실제 변경된 코드 본문은 여전히 Git 저장소(파일)에 있습니다.

   왜 나누어서 저장할까요?
   성능: 수 기가바이트(GB)에 달하는 소스 코드와 바이너리 파일을 RDBMS에 넣으면 DB 성능이 급격히 떨어집니다. 파일은 파일 시스템이 훨씬 잘 다룹니다.

   관계 지향: "누가 이 이슈에 댓글을 달았는가?" 같은 관계형 데이터는 PostgreSQL 같은 RDBMS가 처리하는 것이 압도적으로 유리합니다.

   요약하자면:
   GitLab은 계획과 관리(이슈, 사용자 등)를 위해 PostgreSQL을 쓰고, 실제 결과물(코드, 커밋)을 저장하기 위해 Git(파일 시스템)을 사용합니다.
