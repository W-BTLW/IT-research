# 백엔드 아키텍처: 원시 타입 반환 제한 및 DTO 강제 이유

백엔드 프레임워크와 기업 아키텍처 가이드에서 컨트롤러, 서비스, 컴포넌트 계층 간 원시 타입(`int`, `boolean` 등) 반환을 제한하고, 엄격하게 DTO 및 객체형 리턴을 강제하는 이유는 시스템의 **안정성, 확장성, 표준화, 그리고 보안**을 확보하기 위함.

---

## 1. Null 안전성 결여와 비즈니스 로직 왜곡 방지
* **원시 타입의 한계:** `int` 같은 원시 타입은 데이터 부재 상태를 표현할 수 없어, 값이 없을 때 무조건 `0`을 반환. 혹은 임의로 `-1`로 정의
* **리스크:** 데이터 조회 실패나 권한 부족 상황(`null`)을 `0`으로 오인하여 잔액 오류나 권한 우회 등의 심각한 비즈니스 왜곡으로 이어질 수 있습니다. 객체형을 사용하여 데이터의 존재 여부를 명확히 분리.

## 2. API 및 내부 서비스 간 확장성 확보
* **유연한 변경 수용:** 단일 값(`int`)을 리턴하던 메서드가 향후 메타데이터(페이징, 상태 코드, 경고 메시지 등)를 함께 내려주어야 할 때, 원시 타입은 구조를 완전히 파괴해야 합니다. DTO를 사용하면 내부 필드만 안전하게 확장할 수 있습니다.

## 3. 프레임워크 레벨의 부가 기능 적용
* **자동화된 보안 처리:** 인터셉터나 AOP, 시큐리티 계층에서 응답 본문 암호화, 민감정보 마스킹, 감사 로그(Audit Log) 등을 수행하려면 대상 데이터가 객체(프로퍼티/필드 구조)여야 제어가 가능합니다.

## 4. 공통 응답 포맷 및 전역 예외 처리(`@RestControllerAdvice`)의 안정성
* **표준 래퍼 구조 보장:** `ApiResponse<T>` 같은 공통 응답 폼에 객체를 담아야 `ResponseBodyAdvice` 등이 정상 작동합니다.
* **에러 응답 파괴 방지:** 원시 타입을 직접 반환하면 예외 발생 시 프레임워크가 JSON 기반의 구조화된 에러 메시지를 내려주지 못하고 텍스트 유출이나 타입 캐스팅 예외를 유발합니다.

## 5. 정보 노출(Information Disclosure) 차단
* **내부 설계도 보호:** 원시 타입 에러나 날것의 예외 메시지가 그대로 클라이언트에 노출되면 프레임워크 버전, DB 스키마 구조가 공격자에게 힌트로 제공됩니다. 엄격한 DTO와 공통 예외 응답을 통해 내부 시스템의 흔적을 원천 차단합니다.
