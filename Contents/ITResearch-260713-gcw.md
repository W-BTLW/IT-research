# IaaS와 PaaS의 정의 및 차이점

## 1. 개요

클라우드 컴퓨팅 서비스는 제공되는 관리 범위에 따라 주로 다음과 같이 구분된다.

* IaaS: Infrastructure as a Service
* PaaS: Platform as a Service
* SaaS: Software as a Service

이 중 IaaS와 PaaS는 기업이나 개발자가 애플리케이션을 개발하고 운영할 때 많이 사용하는 클라우드 서비스 모델이다.

IaaS는 서버, 네트워크, 스토리지와 같은 인프라를 제공하며, PaaS는 인프라뿐만 아니라 애플리케이션 실행에 필요한 플랫폼 환경까지 함께 제공한다.

---

## 2. IaaS란?

### 2.1 IaaS 정의

IaaS는 **Infrastructure as a Service**의 약자로, 우리말로는 **서비스형 인프라**라고 한다.

클라우드 사업자가 다음과 같은 IT 인프라를 가상화하여 제공하는 서비스이다.

* 가상 서버
* CPU
* 메모리
* 스토리지
* 네트워크
* 방화벽
* 로드밸런서
* 가상화 환경

사용자는 물리 서버를 직접 구매하거나 데이터센터를 구축하지 않고도 필요한 만큼의 서버 자원을 사용할 수 있다.

다만 운영체제 설치, 미들웨어 구성, 애플리케이션 배포와 같은 작업은 사용자가 직접 관리해야 한다.

### 2.2 IaaS 관리 범위

클라우드 제공업체가 관리하는 영역은 다음과 같다.

* 물리 서버
* 스토리지 장비
* 네트워크 장비
* 데이터센터
* 가상화 기술

사용자가 관리하는 영역은 다음과 같다.

* 운영체제
* 보안 패치
* 미들웨어
* 런타임
* 데이터베이스
* 애플리케이션
* 애플리케이션 데이터

### 2.3 IaaS 예시

대표적인 IaaS 서비스는 다음과 같다.

* Amazon EC2
* Microsoft Azure Virtual Machines
* Google Compute Engine
* 네이버 클라우드 서버
* NHN Cloud Instance

예를 들어 Amazon EC2를 사용하면 사용자가 원하는 CPU, 메모리, 운영체제, 디스크 용량을 선택하여 가상 서버를 생성할 수 있다.

---

## 3. IaaS의 장점

### 3.1 높은 자유도

사용자가 운영체제와 소프트웨어를 직접 설치할 수 있어 시스템 구성을 자유롭게 설계할 수 있다.

기존에 사용하던 온프레미스 서버 환경과 비슷한 방식으로 구성할 수 있다는 장점이 있다.

### 3.2 초기 구축 비용 절감

물리 서버와 네트워크 장비를 직접 구매하지 않아도 되므로 초기 인프라 구축 비용을 줄일 수 있다.

### 3.3 빠른 자원 확장

서비스 사용량이 증가하면 CPU, 메모리, 서버 수량 등을 비교적 빠르게 확장할 수 있다.

반대로 사용량이 감소하면 자원을 축소하여 비용을 절감할 수 있다.

### 3.4 기존 시스템 이전에 유리

온프레미스에서 운영하던 시스템을 클라우드로 이전할 때 기존 서버 구조를 크게 변경하지 않고 이전할 수 있다.

이를 일반적으로 리프트 앤 시프트 방식이라고 한다.

---

## 4. IaaS의 단점

### 4.1 운영 관리 부담

운영체제 설치, 보안 패치, 미들웨어 설정, 장애 대응 등을 사용자가 직접 수행해야 한다.

따라서 서버와 네트워크에 대한 전문 지식이 필요하다.

### 4.2 보안 설정 책임

방화벽, 계정 권한, 서버 접근 제어, 운영체제 보안 설정 등을 사용자가 직접 관리해야 한다.

설정이 잘못되면 외부 공격이나 정보 유출이 발생할 수 있다.

### 4.3 관리 인력 필요

클라우드 사업자가 물리 인프라는 관리하지만 서버 운영 자체는 사용자의 책임이므로 인프라 운영 인력이 필요하다.

### 4.4 비용 관리의 어려움

필요 이상의 서버를 생성하거나 사용하지 않는 자원을 삭제하지 않으면 비용이 계속 발생할 수 있다.

---

## 5. PaaS란?

### 5.1 PaaS 정의

PaaS는 **Platform as a Service**의 약자로, 우리말로는 **서비스형 플랫폼**이라고 한다.

PaaS는 애플리케이션을 개발하고 실행하기 위해 필요한 환경을 클라우드 사업자가 제공하는 서비스이다.

클라우드 사업자가 다음과 같은 영역을 관리한다.

* 서버
* 네트워크
* 스토리지
* 운영체제
* 미들웨어
* 런타임
* 개발 및 배포 환경

개발자는 서버나 운영체제를 직접 관리하지 않고 애플리케이션 개발과 배포에 집중할 수 있다.

### 5.2 PaaS 관리 범위

클라우드 제공업체가 관리하는 영역은 다음과 같다.

* 물리 서버
* 네트워크
* 스토리지
* 가상화
* 운영체제
* 미들웨어
* 런타임
* 애플리케이션 실행 환경

사용자가 관리하는 영역은 다음과 같다.

* 애플리케이션 코드
* 애플리케이션 설정
* 애플리케이션 데이터

### 5.3 PaaS 예시

대표적인 PaaS 서비스는 다음과 같다.

* Google App Engine
* Microsoft Azure App Service
* AWS Elastic Beanstalk
* Heroku
* Red Hat OpenShift
* Cloud Foundry

예를 들어 Azure App Service를 사용하면 개발자가 작성한 Java, Python, Node.js 등의 애플리케이션을 서버 운영체제 설정 없이 배포할 수 있다.

---

## 6. PaaS의 장점

### 6.1 개발 생산성 향상

서버 설치, 운영체제 설정, 미들웨어 구성 작업이 줄어들기 때문에 개발자는 애플리케이션 개발에 집중할 수 있다.

### 6.2 빠른 배포

개발한 소스 코드를 플랫폼에 업로드하거나 Git 저장소와 연결하면 애플리케이션을 빠르게 배포할 수 있다.

### 6.3 인프라 관리 부담 감소

운영체제 보안 패치, 런타임 업데이트, 서버 장애 처리 등의 많은 부분을 클라우드 제공업체가 관리한다.

### 6.4 자동 확장 지원

서비스 사용량에 따라 애플리케이션 인스턴스를 자동으로 늘리거나 줄이는 기능을 제공하는 경우가 많다.

### 6.5 표준화된 개발 환경

개발, 테스트, 운영 환경을 동일한 플랫폼으로 구성할 수 있어 환경 차이로 발생하는 문제를 줄일 수 있다.

---

## 7. PaaS의 단점

### 7.1 낮은 시스템 자유도

사용자가 운영체제나 미들웨어를 직접 제어하기 어렵다.

특정 운영체제 설정이나 커스텀 모듈이 필요한 경우 제약이 발생할 수 있다.

### 7.2 플랫폼 종속성

특정 PaaS에서 제공하는 기능을 많이 사용할수록 다른 클라우드 서비스로 이전하기 어려워질 수 있다.

이를 벤더 종속 또는 벤더 락인이라고 한다.

### 7.3 지원 기술의 제한

PaaS가 지원하는 프로그래밍 언어, 프레임워크, 런타임 버전만 사용할 수 있는 경우가 있다.

예를 들어 특정 Java 버전이나 특정 데이터베이스 연결 방식이 지원되지 않을 수 있다.

### 7.4 장애 원인 분석의 어려움

하위 운영체제나 플랫폼 내부에 직접 접근하기 어려워 장애가 발생했을 때 세부적인 원인을 분석하는 데 한계가 있을 수 있다.

### 7.5 비용 예측의 어려움

트래픽, 실행 시간, 인스턴스 수, 데이터 전송량 등에 따라 비용이 달라질 수 있다.

---

## 8. IaaS와 PaaS의 차이점

| 구분         | IaaS                        | PaaS                      |
| ---------- | --------------------------- | ------------------------- |
| 전체 명칭      | Infrastructure as a Service | Platform as a Service     |
| 의미         | 서비스형 인프라                    | 서비스형 플랫폼                  |
| 주요 제공 범위   | 서버, 스토리지, 네트워크              | 인프라, 운영체제, 미들웨어, 런타임      |
| 운영체제 관리    | 사용자                         | 클라우드 제공업체                 |
| 미들웨어 관리    | 사용자                         | 클라우드 제공업체                 |
| 애플리케이션 관리  | 사용자                         | 사용자                       |
| 인프라 제어 권한  | 높음                          | 낮음                        |
| 개발 편의성     | 상대적으로 낮음                    | 높음                        |
| 운영 부담      | 높음                          | 낮음                        |
| 시스템 구성 자유도 | 높음                          | 상대적으로 낮음                  |
| 적합한 사용자    | 인프라 운영 조직                   | 애플리케이션 개발 조직              |
| 대표 서비스     | Amazon EC2, Azure VM        | Azure App Service, Heroku |

---

## 9. 관리 영역 비교

다음은 각 서비스 모델별 관리 주체를 나타낸 것이다.

| 관리 영역  | 온프레미스 | IaaS | PaaS | SaaS |
| ------ | ----- | ---- | ---- | ---- |
| 애플리케이션 | 사용자   | 사용자  | 사용자  | 제공업체 |
| 데이터    | 사용자   | 사용자  | 사용자  | 제공업체 |
| 런타임    | 사용자   | 사용자  | 제공업체 | 제공업체 |
| 미들웨어   | 사용자   | 사용자  | 제공업체 | 제공업체 |
| 운영체제   | 사용자   | 사용자  | 제공업체 | 제공업체 |
| 가상화    | 사용자   | 제공업체 | 제공업체 | 제공업체 |
| 서버     | 사용자   | 제공업체 | 제공업체 | 제공업체 |
| 스토리지   | 사용자   | 제공업체 | 제공업체 | 제공업체 |
| 네트워크   | 사용자   | 제공업체 | 제공업체 | 제공업체 |

IaaS는 물리 인프라만 제공받고 운영체제부터는 사용자가 관리한다.

PaaS는 애플리케이션 실행 환경까지 제공받기 때문에 사용자는 애플리케이션과 데이터 중심으로 관리하면 된다.

## 10. 실제 구성 예시

### 10.1 IaaS 기반 구성

Spring Boot 애플리케이션을 IaaS 환경에 구축한다고 가정하면 다음과 같은 작업이 필요하다.

1. 가상 서버 생성
2. 운영체제 설치 및 설정
3. Java 설치
4. Tomcat 또는 애플리케이션 실행 환경 구성
5. 방화벽 및 네트워크 설정
6. 애플리케이션 배포
7. 로그 및 모니터링 설정
8. 운영체제와 Java 보안 패치
9. 장애 발생 시 서버 상태 확인

IaaS에서는 사용자가 서버에 SSH로 접속하여 대부분의 설정을 직접 수행한다.

### 10.2 PaaS 기반 구성

동일한 Spring Boot 애플리케이션을 PaaS 환경에 구축하면 다음과 같은 방식으로 진행할 수 있다.

1. PaaS 서비스 생성
2. Java 런타임 버전 선택
3. 애플리케이션 빌드
4. JAR 또는 WAR 파일 배포
5. 환경변수와 데이터베이스 연결정보 설정
6. 애플리케이션 실행

운영체제 설치, Java 설치, Tomcat 구성 등은 플랫폼에서 관리하므로 개발자는 애플리케이션 배포에 집중할 수 있다.

---

## 11. IaaS가 적합한 경우

다음과 같은 경우에는 IaaS가 적합하다.

* 운영체제 설정을 직접 제어해야 하는 경우
* 특정 미들웨어나 라이브러리를 설치해야 하는 경우
* 기존 온프레미스 시스템을 클라우드로 이전하는 경우
* 서버와 네트워크 구성을 세부적으로 관리해야 하는 경우
* 보안 정책상 서버 내부 설정을 직접 관리해야 하는 경우
* 레거시 시스템을 운영해야 하는 경우
* 자체적인 모니터링 및 배포 체계가 구축되어 있는 경우

예를 들어 특정 버전의 Tomcat, JDK, 상용 솔루션을 설치해야 한다면 PaaS보다 IaaS가 적합할 수 있다.

---

## 12. PaaS가 적합한 경우

다음과 같은 경우에는 PaaS가 적합하다.

* 빠르게 서비스를 개발하고 배포해야 하는 경우
* 서버 운영 인력이 부족한 경우
* 개발자가 인프라보다 애플리케이션 개발에 집중해야 하는 경우
* 웹 애플리케이션이나 API 서버를 운영하는 경우
* 트래픽에 따라 자동 확장이 필요한 경우
* 표준적인 프로그래밍 언어와 프레임워크를 사용하는 경우
* 운영체제와 미들웨어 관리 부담을 줄이고 싶은 경우

예를 들어 일반적인 Spring Boot 기반 REST API 서버를 빠르게 배포하려는 경우 PaaS를 활용하면 서버 구축 작업을 줄일 수 있다.

---

## 13. IaaS와 PaaS 선택 기준

IaaS와 PaaS 중 어떤 서비스를 선택해야 하는지는 시스템의 특성과 운영 환경에 따라 달라진다.

### IaaS를 선택해야 하는 경우

* 시스템 제어 권한이 중요한 경우
* 운영체제 설정을 직접 변경해야 하는 경우
* 기존 시스템과 동일한 구조가 필요한 경우
* 자체 운영 인력과 기술력이 충분한 경우

### PaaS를 선택해야 하는 경우

* 개발 속도가 중요한 경우
* 운영 관리 부담을 줄이고 싶은 경우
* 표준화된 애플리케이션을 운영하는 경우
* 인프라 관리보다 서비스 개발에 집중하고 싶은 경우

결국 IaaS는 자유도와 제어권이 높은 대신 관리 부담이 크고, PaaS는 관리가 편리한 대신 시스템 설정의 자유도가 낮다.

---

## 14. 핵심 정리

IaaS는 서버, 네트워크, 스토리지와 같은 인프라를 제공하는 서비스이다.

사용자는 운영체제부터 애플리케이션까지 직접 관리하기 때문에 높은 자유도와 제어권을 가진다. 하지만 서버 운영, 보안 패치, 장애 대응 등에 대한 관리 부담이 발생한다.

PaaS는 인프라뿐만 아니라 운영체제, 미들웨어, 런타임과 같은 애플리케이션 실행 환경까지 제공한다.

개발자는 인프라 관리 부담을 줄이고 애플리케이션 개발과 배포에 집중할 수 있다. 하지만 플랫폼에서 지원하지 않는 기술을 사용하기 어렵고 특정 클라우드 서비스에 종속될 가능성이 있다.

한 문장으로 정리하면 다음과 같다.

> IaaS는 서버를 빌려서 직접 구성하는 방식이고, PaaS는 애플리케이션을 실행할 수 있는 완성된 개발 및 운영 환경을 빌리는 방식이다.
