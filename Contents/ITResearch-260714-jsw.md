좋은 단위 테스트란 무엇인가

프로젝트 초기에 테스트는 종종 귀찮은 작업으로 여겨진다. 기능 하나를 구현하는 데도 테스트 코드를 추가로 작성해야 하고, 실행 시간도 늘어나기 때문이다. 하지만 프로젝트 규모가 커질수록 테스트의 가치는 점점 커진다.

테스트가 없는 프로젝트는 초반에는 빠르게 개발할 수 있다. 그러나 기능이 쌓일수록 기존 코드에 대한 확신이 사라지고, 작은 수정 하나에도 예상하지 못한 버그가 발생한다. 결국 새로운 기능을 추가하는 시간보다 기존 기능을 검증하고 수정하는 시간이 더 많이 소요된다.

반대로 좋은 테스트는 이러한 문제를 막아주는 안전망 역할을 한다. 리팩터링을 부담 없이 수행할 수 있고, 코드 변경에 대한 자신감을 얻을 수 있으며, 프로젝트가 성장하더라도 개발 속도를 일정 수준 유지할 수 있다.

하지만 모든 테스트가 프로젝트에 도움이 되는 것은 아니다. 품질이 낮은 테스트는 오히려 유지보수 비용을 증가시키고 개발 속도를 저하시킨다. 결국 중요한 것은 테스트를 많이 작성하는 것이 아니라 좋은 테스트를 작성하는 것이다.

⸻

AAA 패턴으로 테스트를 구조화하기

좋은 단위 테스트는 대부분 AAA 패턴을 따른다.

* Arrange : 테스트에 필요한 객체와 데이터를 준비한다.
* Act : 테스트 대상 메서드를 실행한다.
* Assert : 실행 결과가 기대한 값과 일치하는지 검증한다.

이처럼 준비, 실행, 검증을 명확하게 구분하면 테스트의 의도가 한눈에 드러난다. 다른 개발자가 테스트를 읽더라도 어떤 상황에서 어떤 동작을 수행했고 무엇을 검증하는지 쉽게 이해할 수 있다.

TDD를 적용하는 경우에는 Arrange보다 Assert를 먼저 작성하는 것도 좋은 방법이다. 구현보다 먼저 “어떤 결과가 나와야 하는가”를 정의하면 기능의 목적이 더욱 명확해지고 불필요한 구현을 줄일 수 있다.

⸻

하나의 테스트는 하나의 행동만 검증해야 한다

하나의 테스트 안에 여러 개의 Arrange, Act, Assert가 반복된다면 테스트가 너무 많은 것을 검증하고 있다는 신호일 수 있다.

예를 들어 회원 가입, 로그인, 권한 확인까지 하나의 테스트에서 모두 수행한다면 어느 단계에서 문제가 발생했는지 파악하기 어렵다. 하나의 검증이 실패했을 때 테스트 전체가 실패하기 때문에 원인 분석에도 시간이 오래 걸린다.

좋은 단위 테스트는 하나의 행동만 검증한다.

* 회원 가입이 정상적으로 수행되는가
* 로그인이 정상적으로 수행되는가
* 권한 검증이 정상적으로 이루어지는가

처럼 각각을 독립된 테스트로 분리하는 것이 바람직하다.

테스트 하나가 하나의 책임만 가지도록 유지하면 테스트의 가독성과 유지보수성이 크게 향상된다.

⸻

Act가 복잡하다면 프로덕트 코드를 의심해 볼 필요가 있다

Act 영역은 가능하면 하나의 공개 API 호출로 끝나는 것이 이상적이다.

예를 들어 상품을 구매하는 기능을 테스트한다고 가정해 보자.

purchase();
removeInventory();

처럼 두 개의 메서드를 호출해야만 구매가 정상적으로 완료된다면 테스트보다 프로덕트 코드의 설계를 먼저 살펴볼 필요가 있다.

비즈니스 관점에서 상품 구매는 하나의 행동이다. 구매가 성공했다면 재고 감소, 결제 처리, 주문 생성 등의 후속 작업은 모두 내부에서 함께 이루어져야 한다.

즉, 테스트가 여러 개의 공개 메서드를 순서대로 호출해야 한다면 애플리케이션 역시 잘못 사용할 가능성이 존재한다.

좋은 테스트는 좋은 설계를 요구한다. 테스트가 복잡하다면 테스트를 수정하기보다 설계를 개선하는 것이 근본적인 해결책인 경우가 많다.

⸻

구현이 아니라 요구사항을 테스트해야 한다

테스트가 내부 구현을 지나치게 많이 알고 있으면 작은 리팩터링에도 쉽게 깨진다.

예를 들어 카드 덱에서 카드가 모두 소진되면 예외가 발생하는지 확인하고 싶다고 가정해 보자.

다음과 같은 테스트는 구현에 강하게 의존한다.

* 카드가 52장이라는 사실을 알고 있다.
* draw()가 항상 한 장씩 뽑는다는 사실을 알고 있다.
* 52번 반복 호출한 뒤 한 번 더 호출한다.

현재는 동작하지만 카드 개수가 변경되거나 여러 장을 한 번에 뽑는 기능이 추가되는 순간 테스트는 모두 실패하게 된다.

테스트가 검증해야 하는 것은 “52장을 모두 뽑았다”가 아니라 “덱이 비어 있다”는 상태이다.

즉, 테스트는 구현 방식이 아니라 요구사항과 비즈니스 규칙을 검증해야 한다.

이러한 테스트를 작성하려면 객체가 원하는 상태를 쉽게 만들 수 있도록 설계를 개선하는 것이 도움이 된다. 생성 전략이나 의존성 주입과 같은 방법을 활용하면 테스트는 내부 구현을 몰라도 필요한 상황을 쉽게 만들 수 있다.

⸻

좋은 테스트는 좋은 설계를 만든다

테스트를 작성하다 보면 자연스럽게 설계상의 문제를 발견하게 된다.

* 하나의 메서드가 너무 많은 책임을 가진다.
* 객체를 원하는 상태로 만들기 어렵다.
* 내부 구현에 지나치게 의존한다.
* 공개 API가 비즈니스 개념과 맞지 않는다.

이러한 문제를 해결하는 과정에서 객체의 책임은 더욱 명확해지고 결합도는 낮아진다.

결국 테스트는 단순히 버그를 찾기 위한 도구가 아니라 설계 품질을 점검하는 역할도 수행한다.

⸻

마무리

좋은 단위 테스트는 코드의 동작을 검증하는 것을 넘어 프로젝트의 유지보수성을 높이는 역할을 한다.

좋은 테스트를 작성하기 위해서는 다음 원칙을 기억하면 된다.

* Arrange, Act, Assert를 명확하게 구분한다.
* 하나의 테스트는 하나의 행동만 검증한다.
* Act가 복잡하다면 설계를 다시 살펴본다.
* 구현이 아니라 요구사항을 검증한다.
* 테스트하기 어려운 코드는 설계 개선의 신호로 받아들인다.

테스트는 개발 속도를 늦추기 위한 작업이 아니라, 시간이 지나도 개발 속도를 유지하기 위한 투자이다. 결국 오래 살아남는 프로젝트는 테스트를 많이 작성한 프로젝트가 아니라, 좋은 테스트를 꾸준히 작성한 프로젝트이다.
