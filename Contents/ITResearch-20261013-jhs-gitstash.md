# `git pull` vs `git rebase` 비교 및 `git stash`를 활용한 충돌 해결법

## 1. `git pull` vs `git rebase` 비교 분석

### 1.1 `git pull` (기본 동작: Fetch + Merge)

* **특징:** 원격 저장소의 최신 변경 사항을 수신한 후 로컬 브랜치와 병합(Merge)을 수행함.
* **결과:** 병합 커밋(Merge Commit)이 명시적으로 생성됨.
* **장단점:**
  * 장점: 브랜치의 분기 및 병합 이력이 보존됨.
  * 단점: 빈번한 pull 수행 시 불필요한 머지 커밋이 다수 발생하여 커밋 히스토리의 가독성이 저하됨.

### 1.2 `git pull --rebase` (Fetch + Rebase)

* **특징:** 원격 저장소의 최신 변경 사항을 베이스(Base)로 재설정한 후, 로컬의 신규 커밋을 그 위에 순차적으로 재적용(Replay)함.
* **결과:** 머지 커밋 없이 단선형(Linear) 히스토리를 유지함.
* **장단점:**
  * 장점: 커밋 히스토리가 정돈되어 추적이 용이함.
  * 단점: 재적용 과정에서 각 커밋마다 충돌이 발생할 수 있어 해소 절차가 다소 복잡할 수 있음.

## 2. `git stash` 개요 및 활용 목적

작업 디렉토리(Working Directory) 내 미완성된 변경 사항(Modified 및 Staged 파일)을 임시 저장소에 보관하고, 작업 환경을 가장 최근의 커밋(`HEAD`) 상태로 복구하는 명령어임.

### 2.2 주요 활용법

* 작업 도중 다른 긴급 이슈(Hotfix) 대응을 위해 브랜치를 전환해야 하는 경우
* 커밋 단위로 묶기에는 미완성된 코드가 존재하여 임시 보관이 필요한 경우
* 원격 최신 코드를 반영(`pull`)하는 과정에서 작업 중인 파일과의 충돌을 예방하고자 하는 경우

## 3. `git stash` 기반 충돌 해결 표준 절차

로컬 작업 내역이 존재하는 상태에서 원격 저장소 코드를 동기화할 때 발생할 수 있는 충돌 및 작업 거부 현상을 방지하기 위한 표준 절차는 다음과 같음.

### [1단계] 작업 내역 임시 저장

작업 중인 변경 사항을 스태시(Stash) 영역으로 이동시킴.

```bash
git stash
```

* **검증:** `git status` 실행 시 작업 디렉토리가 깨끗한 상태(`working tree clean`)임을 확인함.

### [2단계] 원격 최신 코드 반영

로컬 변경 사항이 제거된 상태에서 원격 저장소의 코드를 반영함.

```bash
git pull --rebase
```

* **검증:** `Successfully rebased and updated` 메시지 출력을 확인함.

### [3단계] 임시 저장 내역 재적용

스태시에 보관된 변경 사항을 불러와 최신 코드 위에 적용함.

```bash
git stash pop
```

* **검증:** 충돌이 없는 경우 자동 병합이 완료됨. 충돌 발생 시 다음 단계를 진행함.

### [4단계] 충돌(Conflict) 해소

충돌이 발생한 파일 내 충돌 마커를 확인하고 최종 코드를 확정함.

```text
<<<<<<< HEAD (원격 저장소 최신 기준)
원격 수정 코드
=======
내가 작성한 임시 저장(stash) 코드
>>>>>>> stash
```

* **검증:** 파일 내부의 충돌 마커 기호(`<<<<<<<`, `=======`, `>>>>>>>`)를 모두 제거하고 정합성을 검증함.

### [5단계] 변경 사항 스테이징 및 완료

충돌 해소가 완료된 파일을 스테이징 영역에 등록함.

```bash
git add .
```

* **검증:** `git status` 실행을 통해 대상 파일들이 Staged 상태(초록색 표시)로 전환되었는지 확인함.
