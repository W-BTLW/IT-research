# 캐시 스탬피드(Cache Stampede)란?

캐시 스탬피드(Cache Stampede)는 **인기 있는 캐시 키가 만료되는 순간**, 동시에 많은 요청이 백엔드(DB, 외부 API 등)로 몰리면서 시스템 부하가 급격히 커지는 현상입니다. 이때 동일한 데이터를 여러 요청이 한꺼번에 재생성하려고 하면서 DB 과부하나 지연이 발생할 수 있습니다.

## 발생 상황

예를 들어 `product:123`의 캐시 TTL이 10분이라고 가정하면, 10분이 지나 캐시가 만료되는 순간 수천 개의 요청이 동시에 `product:123`을 조회할 수 있습니다. 캐시가 비어 있으므로 각 요청이 DB나 외부 API로 바로 접근하게 되고, 그 결과 백엔드에 트래픽이 집중됩니다.
## 문제점

- DB 또는 외부 API 과부하가 발생할 수 있습니다.
- 응답 지연이 커지고, 심하면 장애로 이어질 수 있습니다.
- 동일한 데이터를 여러 번 계산하게 되어 불필요한 비용이 늘어납니다.

## 방지 방법

### 1) 랜덤한 만료 시간 설정
캐시 만료 시간을 고정값으로 두지 않고, 일정 범위에서 랜덤하게 설정해 만료 시점을 분산합니다. 이렇게 하면 여러 캐시가 동시에 만료되는 상황을 줄일 수 있습니다.

### 2) 선제적 갱신
캐시가 만료되기 전에 백그라운드에서 미리 갱신하는 방식입니다. `refreshAfterWrite`처럼 만료 직전 자동 갱신을 지원하는 패턴이 대표적입니다.

### 3) 분산락 사용
최초 1개의 요청만 락을 획득해 백엔드에서 데이터를 다시 만들고, 나머지 요청은 대기하거나 기존 값을 재사용하게 합니다. Redis의 `SETNX` 같은 방식이 자주 사용됩니다.

### 4) 요청 합치기
동시에 들어온 동일 요청을 하나로 합쳐 백엔드 호출을 1번만 수행하는 방식입니다. 요청 수가 많아도 중복 재계산을 줄일 수 있습니다.

## 예시 정리

`product:123` 캐시가 600초 TTL로 설정되어 있고, 600초가 되는 순간 트래픽이 몰리면 수천 개 요청이 동시에 DB를 치게 됩니다. 이 문제를 막으려면 TTL에 지터를 주고, 만료 전에 갱신하고, 필요하면 분산락으로 단일 요청만 재생성하도록 제어하면 됩니다.
## 한줄 정의

캐시 스탬피드는 **캐시 만료 시점에 요청이 한꺼번에 몰려 백엔드가 과부하되는 현상**입니다.
