PHP2Shell: 전 세계 웹 생태계를 위협한 PHP 원격코드 실행 취약점

1. PHP란 무엇인가?

PHP(Hypertext Preprocessor)는 웹 서버에서 실행되는 대표적인 서버 사이드 프로그래밍 언어입니다.

사용자가 웹사이트에 접속하면 웹 서버는 PHP 코드를 실행하고, 데이터베이스 조회나 로그인 인증 등의 작업을 수행한 뒤 그 결과를 HTML 형태로 사용자에게 전달합니다.

쉽게 말해, Java의 Spring Boot가 웹 애플리케이션의 서버 측 로직을 담당하는 것처럼 PHP도 웹 서비스의 핵심 로직을 담당합니다.

PHP가 오랫동안 사랑받은 이유는 다음과 같습니다.

* 낮은 진입장벽: 문법이 비교적 단순하고 별도의 복잡한 개발 환경 없이도 웹 개발을 시작할 수 있습니다.
* 저렴한 운영비: 저렴한 공유 호스팅 환경에서도 PHP를 쉽게 구동할 수 있습니다.
* 풍부한 생태계: WordPress, Drupal, Joomla 등 다양한 CMS(콘텐츠 관리 시스템)가 PHP를 기반으로 개발되었습니다.
* 오랜 역사: 1990년대부터 웹 개발에 활용되면서 방대한 레거시 시스템과 개발 생태계를 형성했습니다.

특히 WordPress는 전 세계 웹사이트의 약 40%에서 사용되는 것으로 알려져 있으며, PHP의 높은 점유율을 뒷받침하는 대표적인 사례입니다.

실제로 W3Techs의 2026년 11월 통계에 따르면 PHP는 서버 사이드 프로그래밍 언어가 확인되는 웹사이트의 약 **69%**에서 사용되고 있습니다.

즉, PHP는 오래된 언어라는 인식과 달리 여전히 전 세계 웹 생태계의 상당 부분을 담당하고 있습니다.

2. PHP2Shell 취약점이란?

2026년 10월 21일, PHP의 핵심 실행 엔진에서 두 가지 치명적인 보안 취약점이 공개되었습니다.

해당 취약점은 PHP2Shell이라는 이름으로 불리며, 다음 두 가지 CVE로 구분됩니다.

* CVE-2026-109618: 메모리 부족(OOM) 처리 과정에서 발생하는 메모리 손상 취약점
* CVE-2026-109619: 요청 처리 과정에서 해제된 메모리의 포인터가 재사용되는 Use-After-Free 취약점

두 취약점 모두 CVSS 4.0 기준 9.2점으로, 최고 등급인 Critical에 해당합니다.

가장 심각한 점은 공격자가 별도의 로그인이나 인증 절차 없이 원격에서 공격을 수행할 수 있다는 것입니다.

또한 특정 웹사이트의 소스코드에 존재하는 취약점이 아니라 PHP 자체의 실행 엔진에서 발생하는 문제이기 때문에, WordPress나 Drupal 같은 개별 애플리케이션뿐 아니라 PHP를 사용하는 다양한 웹서비스가 영향을 받을 수 있습니다.

3. RCE(Remote Code Execution)란 무엇인가?

RCE는 원격코드 실행 취약점을 의미합니다.

쉽게 설명하면 공격자가 자신의 컴퓨터에서 원격 서버에 특정 요청을 보내고, 해당 서버가 공격자가 의도한 명령어를 실행하도록 만드는 취약점입니다.

일반적인 웹서비스에서는 사용자가 HTTP 요청을 보내면 서버가 정해진 프로그램 로직에 따라 응답합니다.

하지만 RCE 취약점이 존재하면 공격자는 정상적인 서비스 로직을 거치지 않고 서버에 임의의 명령을 실행하도록 유도할 수 있습니다.

예를 들어 다음과 같은 상황이 발생할 수 있습니다.

1. 공격자가 취약한 웹 서버에 악의적인 HTTP 요청을 전송합니다.
2. 서버가 취약점을 통해 공격자의 명령을 실행합니다.
3. 공격자는 웹 서버의 파일을 읽거나 수정할 수 있습니다.
4. 서버에 웹셸(Web Shell)을 설치하여 지속적으로 접근할 수 있습니다.
5. 서버에 저장된 개인정보, DB 접속정보, API 인증키 등을 탈취하거나 다른 내부 시스템으로 공격을 확대할 수 있습니다.

즉, 단순히 홈페이지 화면을 변조하는 수준이 아니라 웹 서버 자체가 공격자의 통제하에 놓일 수 있다는 의미입니다.

4. PHP2Shell은 왜 발생했을까? (핵심 원리)

이번 취약점의 핵심은 PHP가 메모리를 할당하고 해제하는 과정에서 예외 상황을 제대로 처리하지 못했다는 점입니다.

개발자가 이해하기 쉽게 설명하면 다음과 같습니다.

일반적으로 프로그램은 작업을 수행하기 위해 메모리를 할당하고, 작업이 끝나면 사용했던 메모리를 해제합니다.

이때 중요한 것은 정상적인 상황뿐 아니라 예외가 발생했을 때도 메모리 상태를 일관성 있게 관리해야 한다는 것입니다.

그런데 PHP에서는 특정 요청을 처리하던 도중 메모리 부족(OOM)이나 치명적인 오류가 발생하면 내부 자료구조가 완전히 초기화되지 않은 상태로 남거나, 이미 해제된 메모리를 가리키는 포인터가 남는 문제가 있었습니다.

이를 두 가지 관점에서 살펴보겠습니다.

① CVE-2026-109618: 메모리 부족 상황에서의 불완전한 초기화

공격자가 특수하게 조작한 HTTP 요청을 보내 PHP에서 메모리 부족 상황을 유도합니다.

이 과정에서 PHP는 정상적인 요청 처리를 중단하고 예외 처리 경로로 빠져나갑니다.

문제는 요청 처리를 정리하는 후속 과정에서 발생합니다.

일부 내부 자료구조가 정상적으로 초기화되지 않았는데도 PHP가 해당 자료구조를 정상적인 상태라고 가정하고 접근하는 것입니다.

비유하자면 객체를 생성하다가 예외가 발생해 생성이 중단되었는데, 소멸자나 정리 코드에서 해당 객체가 완전히 생성되었다고 가정하고 내부 필드를 참조하는 상황과 유사합니다.

이때 메모리의 비정상적인 상태를 공격자가 조작하면 메모리 손상을 유발하고 궁극적으로 임의의 코드 실행까지 이어질 수 있습니다.

② CVE-2026-109619: Use-After-Free 취약점

이 문제는 메모리를 해제한 이후에도 해당 메모리를 가리키는 포인터가 남아 있는 상황입니다.

예를 들어 A라는 객체가 메모리 주소 100번지를 사용하다가 작업이 끝나 메모리가 해제되었다고 가정하겠습니다.

그런데 내부 포인터는 여전히 100번지를 가리키고 있습니다.

이후 다른 객체 B가 우연히 같은 메모리 공간을 할당받아 사용하게 되면, 기존 포인터를 통해 B의 메모리에 접근할 수 있는 상황이 발생합니다.

이를 Use-After-Free라고 합니다.

공격자는 이런 메모리 재사용 상황을 정교하게 유도하여 프로그램이 의도하지 않은 데이터를 읽거나 조작하도록 만들 수 있습니다.

특히 이번 취약점에서는 요청 간에 공유되는 내부 상태가 이전 요청에서 해제된 메모리를 계속 참조할 수 있다는 점이 문제가 되었습니다.

결국 공격자는 이 메모리 관리 오류를 악용하여 PHP 실행 흐름을 조작하고 임의의 코드를 실행할 수 있습니다.

정리하면, 메모리 부족이나 예외가 발생했다는 사실 자체가 취약점은 아닙니다. 예외 발생 이후에도 프로그램 내부 상태와 메모리 참조 관계를 안전하게 정리하지 못했다는 것이 근본적인 문제입니다.

5. 왜 전 세계적으로 큰 파장이 발생했을까?

PHP2Shell이 심각하게 받아들여진 이유는 취약점의 위험성과 PHP의 압도적인 사용 범위가 결합되었기 때문입니다.

대표적인 이유는 다음과 같습니다.

* 압도적인 사용량: 서버 사이드 언어가 확인되는 웹사이트의 약 69%가 PHP를 사용합니다.
* 인증 없는 공격: 별도의 로그인이나 사용자 권한 없이 원격에서 공격을 시도할 수 있습니다.
* 애플리케이션 독립성: WordPress, Drupal 등 특정 제품에 국한되지 않고 PHP 실행 환경 자체가 영향을 받습니다.
* 서버 장악 가능성: 단순한 정보 노출을 넘어 원격코드 실행을 통해 서버 전체의 보안이 무너질 수 있습니다.
* 레거시 시스템 문제: 오랫동안 운영된 PHP 시스템 중에는 보안 업데이트가 제대로 이루어지지 않은 경우가 많습니다.

특히 PHP는 개인 블로그부터 쇼핑몰, 기업 홈페이지, 정부기관 홈페이지까지 폭넓게 사용됩니다.

따라서 특정 기업의 제품 하나에 국한된 취약점이 아니라, 전 세계 웹 인프라에 걸친 문제로 확대될 수 있었습니다.

6. PHP의 열악한 운영 및 유지보수 실태

이번 사태에서 주목할 부분은 PHP 자체의 사용량뿐 아니라 실제 운영 환경의 보안 관리 수준입니다.

PHP는 저렴한 호스팅 환경에서 쉽게 구동할 수 있고 WordPress와 같은 CMS를 통해 비개발자도 웹사이트를 운영할 수 있다는 장점이 있습니다.

반면 이러한 접근성은 운영 주체가 다양하고 보안 관리 수준에 편차가 크다는 문제로 이어질 수 있습니다.

특히 다음과 같은 사례가 대표적입니다.

* 개발 이후 수년간 PHP 버전을 변경하지 않는 레거시 시스템
* 보안 업데이트가 종료된 EOL(End of Life) 버전의 지속적인 사용
* 외주 업체에 개발과 운영을 맡긴 뒤 PHP 버전이나 라이브러리 관리 현황을 파악하지 못하는 경우
* WordPress 플러그인과 테마를 포함한 구성요소의 업데이트 누락
* 저렴한 웹 호스팅 환경에서 여러 웹사이트가 동일한 PHP 실행 환경을 공유하는 경우

SecuSeek가 2026년 PHP2Shell 공개 직후 분석한 자료에 따르면, 조사 대상 중 PHP 버전이 확인되는 웹사이트의 상당수가 이미 지원이 종료된 구버전을 사용하고 있었습니다.

특히 한국의 경우 버전이 공개된 PHP 웹사이트 중 약 75%가 지원 종료된 버전을 사용하는 것으로 조사되었습니다.

다만 이는 전체 국내 웹사이트를 대상으로 한 전수조사 결과가 아니라, 버전이 확인된 조사 대상에 한정된 수치라는 점에 유의해야 합니다.

결국 PHP의 높은 접근성과 오랜 역사로 형성된 방대한 레거시 생태계가 보안 업데이트 측면에서는 관리 부담으로 작용하고 있는 것입니다.

7. 국내 IT 환경은 상대적으로 안전했을까?

국내 대기업이나 공공기관의 핵심 업무 시스템은 Java 기반으로 구축된 경우가 많습니다.

특히 공공기관은 전자정부 표준프레임워크를 중심으로 Java와 Spring 기반의 개발 환경이 널리 사용되고 있습니다.

이러한 국내 개발 환경의 특성상 PHP를 핵심 기술로 사용하는 대규모 업무 시스템의 비중은 상대적으로 낮을 수 있습니다.

따라서 Java 기반의 금융권 핵심 업무 시스템이나 전자정부 표준프레임워크 기반 시스템은 PHP2Shell의 직접적인 영향 범위에서 벗어날 수 있습니다.

하지만 국내에서도 PHP 기반의 중소기업 홈페이지, 쇼핑몰, 커뮤니티, 개인 및 기업 블로그, 외주 운영 시스템 등은 상당수 존재합니다.

특히 외주 개발이나 저렴한 호스팅 환경에서 운영되는 웹서비스는 PHP 버전 관리가 소홀할 가능성이 있습니다.

여기서 중요한 점은 대기업이나 공공기관이라고 해서 무조건 안전한 것은 아니라는 것입니다.

메인 업무 시스템이 Java로 구축되어 있더라도 별도로 운영하는 홈페이지, 고객지원 사이트, 이벤트 페이지, 협력사 시스템 등이 PHP를 사용할 수 있기 때문입니다.

또한 웹사이트의 화면이나 URL만으로 PHP 사용 여부를 판단할 수는 없습니다. 국내 특정 기관이나 기업이 PHP를 사용한다고 단정하려면 실제 기술 스택에 대한 확인이 필요합니다.

8. 과거 Log4Shell과 비교

이번 PHP2Shell은 2021년 12월 전 세계를 뒤흔들었던 Log4Shell 취약점과 자주 비교됩니다.

Log4Shell은 Java 생태계에서 널리 사용되던 로깅 라이브러리인 Apache Log4j의 취약점(CVE-2021-44228)입니다.

공격자가 로그에 특수하게 조작된 문자열을 삽입하면 Log4j의 JNDI 조회 기능을 악용하여 외부에서 악성 코드를 불러와 실행할 수 있었습니다.

특히 Log4j는 수많은 Java 애플리케이션과 기업용 솔루션에 내장되어 있었기 때문에 실제로 어떤 시스템이 해당 라이브러리를 사용하고 있는지 파악하는 것부터 어려운 문제였습니다.

두 취약점을 비교하면 다음과 같습니다.

구분	PHP2Shell	Log4Shell
공개 시점	2026년 10월	2021년 12월
대상	PHP 실행 엔진	Apache Log4j2
주요 취약점	메모리 손상, Use-After-Free	JNDI 조회 및 입력값 처리
공격 방식	조작된 HTTP 요청	조작된 로그 입력값
인증 필요 여부	불필요	불필요

9. 대응 방법

이번 취약점은 PHP 실행 엔진 자체의 문제이므로 WordPress나 개별 웹 애플리케이션만 업데이트해서는 해결되지 않습니다.

PHP 실행 환경을 취약점이 수정된 최신 보안 버전으로 업데이트하는 것이 근본적인 해결책입니다.

주요 수정 버전은 다음과 같습니다.

* PHP 8.5.12 이상
* PHP 8.4.27 이상
* PHP 8.3.36 이상
* PHP 8.2.35 이상

PHP 8.1 이하의 경우 공식 지원이 종료된 버전이 있으므로 배포판이나 공급업체의 보안 패치 제공 여부를 확인하고, 지원되는 버전으로 업그레이드하는 것이 권장됩니다.

단, 이미 공격에 노출된 서버라면 패치 적용만으로 기존 침해 흔적이 제거되는 것은 아니므로 별도의 침해 여부 확인도 필요합니다.

10. 마무리

PHP2Shell은 특정 웹사이트의 개발 실수나 개별 애플리케이션의 취약점이 아니라, 전 세계적으로 사용되는 프로그래밍 언어의 핵심 실행 엔진에서 발생한 보안 취약점이라는 점에서 의미가 큽니다.

특히 메모리 관리와 예외 처리라는 비교적 저수준의 문제 하나가 원격코드 실행이라는 치명적인 보안 사고로 이어질 수 있다는 점을 보여준 사례입니다.

또한 이번 사건은 최신 기술을 도입하는 것만큼이나 기존 시스템의 버전 관리와 보안 패치가 중요하다는 사실을 다시 한번 일깨워 주었습니다.

결국 보안은 새로운 기술을 얼마나 잘 사용하는가뿐만 아니라, 이미 사용하고 있는 기술을 얼마나 책임감 있게 관리하는가의 문제이기도 합니다.
