로드밸런싱(Load Balancing)이란 무엇인가?

웹 서비스를 개발하다 보면 처음에는 서버 한 대로 충분하다.

사용자 → 웹 서버

하지만 서비스가 성장하면 상황이 달라진다.

예를 들어 서버 한 대가 동시에 처리할 수 있는 요청이 초당 1,000건이라고 가정해보자. 사용자가 늘어나 초당 10,000건의 요청이 들어오면 서버는 더 이상 감당할 수 없게 된다.

이때 가장 단순한 해결책은 서버를 여러 대로 늘리는 것이다.

사용자
  ↓
???
 ↓ ↓ ↓
서버1
서버2
서버3

그런데 새로운 문제가 생긴다.

사용자는 어떤 서버로 접속해야 할까?

서버1이 바쁜지 서버2가 한가한지 사용자는 알 수 없다.

이 문제를 해결하기 위해 등장한 것이 로드밸런서(Load Balancer)이다.

⸻

로드밸런서의 역할

로드밸런서는 사용자와 서버 사이에서 요청을 적절한 서버로 분배하는 장치 또는 소프트웨어이다.

사용자
   ↓
로드밸런서
 ↓  ↓  ↓
서버1 서버2 서버3

사용자는 로드밸런서만 바라본다.

로드밸런서는 현재 서버들의 상태를 확인하고 적절한 서버로 요청을 전달한다.

쉽게 말하면 “교통정리 담당자”라고 생각하면 된다.

⸻

왜 필요한가?

1. 트래픽 분산

서버 한 대에 요청이 몰리는 것을 방지할 수 있다.

예를 들어 3대의 서버가 있다면

1000명
 ↓
로드밸런서
 ↓ ↓ ↓
333명
333명
334명

처럼 요청을 나누어 처리할 수 있다.

⸻

2. 장애 대응

서버2가 죽었다고 가정해보자.

서버1 (정상)
서버2 (장애)
서버3 (정상)

로드밸런서는 주기적으로 서버 상태를 점검한다.

이를 Health Check라고 부른다.

서버2가 응답하지 않으면 요청을 보내지 않는다.

사용자
   ↓
로드밸런서
 ↓      ↓
서버1   서버3

덕분에 서비스 전체가 중단되지 않는다.

⸻

3. 무중단 배포

운영 중인 서비스를 배포할 때도 활용된다.

예를 들어 서버 3대가 있다고 하자.

1. 서버1 제외
2. 서버1 배포
3. 서버1 정상 확인
4. 서버2 제외
5. 서버2 배포
6. 서버3 반복

이 과정을 통해 서비스를 중단하지 않고 배포할 수 있다.

⸻

대표적인 분배 방식

Round Robin

가장 단순한 방식이다.

1번 요청 → 서버1
2번 요청 → 서버2
3번 요청 → 서버3
4번 요청 → 서버1

순서대로 분배한다.

⸻

Least Connection

현재 연결 수가 가장 적은 서버로 보낸다.

서버1 : 100개 연결
서버2 : 20개 연결
서버3 : 50개 연결

이라면 서버2로 요청을 전달한다.

⸻

Weighted Round Robin

서버 성능이 서로 다를 때 사용한다.

서버1 : 가중치 5
서버2 : 가중치 3
서버3 : 가중치 2

서버1이 더 많은 요청을 받게 된다.

⸻

L4 로드밸런서와 L7 로드밸런서

실무에서는 자주 듣게 되는 용어이다.

L4 Load Balancer

TCP/IP 계층 정보를 보고 분배한다.

IP
PORT

기준으로 동작한다.

속도가 빠르다.

대표적으로 금융권이나 대규모 서비스의 전면에 배치되는 경우가 많다.

⸻

L7 Load Balancer

HTTP 요청 내용을 이해할 수 있다.

예를 들어

/api/*

는 API 서버로 보내고

/image/*

는 이미지 서버로 보내는 것이 가능하다.

사용자
 ↓
L7
 ↓
/api → API 서버
/image → 이미지 서버

이런 기능 때문에 웹 서비스에서 많이 사용된다.

⸻

실무에서 자주 듣는 용어

Health Check

로드밸런서가 서버 생존 여부를 확인하는 기능

GET /health

같은 URI를 주기적으로 호출한다.

⸻

Sticky Session

한 사용자를 계속 같은 서버로 보내는 기능

세션 기반 로그인 환경에서 자주 사용된다.

⸻

Active-Active

모든 서버가 동시에 서비스

서버1
서버2
서버3

전부 요청 처리

⸻

Active-Standby

주 서버 장애 시 대기 서버가 대신 동작

주 서버
 ↓ 장애
대기 서버 활성화

⸻

개발자가 알아야 하는 이유

백엔드 개발자라고 해서 로드밸런서를 몰라도 되는 것은 아니다.

실제 운영 환경에서는 다음과 같은 문제가 자주 발생한다.

* 특정 서버만 CPU가 높다.
* 로그인 후 로그아웃된다.
* Health Check 때문에 트래픽이 발생한다.
* 특정 서버로만 요청이 몰린다.
* L4에서는 되는데 L7에서는 안 된다.
* 클라이언트 IP가 사라진다.
* 무중단 배포가 실패한다.

이런 문제들은 대부분 로드밸런서의 동작 원리를 이해하면 원인을 추적할 수 있다.

로드밸런서는 단순히 “요청을 나눠주는 장비”가 아니라, 실제 서비스의 가용성과 안정성을 책임지는 핵심 구성 요소라고 볼 수 있다.
