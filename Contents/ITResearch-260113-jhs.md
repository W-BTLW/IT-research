# 중복트랜잭션ID 에러는 왜 날까?

## 안드로이드의 http 라이브러리 OkHttp

안드로이드의 OkHttp는 성능과 효율을 최우선으로 설계된 라이브러리

- 공격적인 재시도: iOS의 URLSession은 네트워크 에러 시 개발자에게 제어권을 넘기고 대기하는 편이지만, OkHttp는 retryOnConnectionFailure 옵션이 기본적으로 활성화되어 있어 시스템 판단하에 스스로 재시도를 수행.

- 커넥션 풀링(Connection Pooling): 이전에 성공한 연결 통로를 재사용하는 능력이 매우 뛰어남. 이 과정에서 죽은 줄 몰랐던 연결을 사용했다가 에러가 나면, 사용자 몰래 새 연결을 만들어 기존 요청(Transaction ID 포함)을 복제해 전송.

- 로그의 밀집도: 재시도 속도가 매우 빠르기 때문에, 로그상에는 동일한 요청이 '따닥'하고 붙어서 발생하는 것처럼 보일때도 있음.

## OkHttp가 자동 재시도를 수행하는 조건
단순히 응답이 늦는다고 다시 보내는 것이 아니라, "이 요청은 서버에 전달되지 않았을 가능성이 있다"라고 판단할 때 재시도.

- 다중 IP 환경: 서버 도메인에 연결된 IP가 여러 개일 때, 첫 번째 IP(A) 연결에 실패하면 즉시 두 번째 IP(B)로 재시도.

- Connection Stale(연결 만료): 커넥션 풀에 있던 기존 소켓이 서버에 의해 이미 끊겼는데, 앱이 이를 모르고 패킷을 실어 보냈다가 IOException이 발생한 경우.

- SSL/TLS 핸드쉐이크 실패: 보안 연결 과정에서 일시적인 오류가 발생하여 경로를 변경해야 할 때 재시도.

**핵심 문제점** : 패킷은 이미 서버에 도착해 로직이 실행 중인데, 클라이언트가 응답을 받기 직전에 네트워크 연결이 미세하게 끊기면 OkHttp는 이를 "전송 실패"로 오해하고 동일한 데이터를 다시 보냄 -> 트랜잭션ID 중복 에러남.

## 중복 요청 방지 해결책

① 클라이언트단 (AOS/OkHttp)
자동 재시도 비활성화: 결제나 주문처럼 중복되면 안 되는 API를 처리하는 OkHttpClient 설정에서 재시도를 명시적으로 OFF.


```java
val client = OkHttpClient.Builder()
    .retryOnConnectionFailure(false) // 자동 재시도 방지
    .build()
```

② 서버단 (Backend)
서버에서 **Transaction ID를 체크하는 '멱등성(Idempotency) 로직'**을 강화.

```
서버가 요청을 받으면 Transaction ID를 DB나 Redis에 저장(Lock).

동일한 ID로 요청이 또 들어오면, "이미 처리 중"이거나 "이미 완료된" 건으로 간주하여 실제 로직을 태우지 않고 성공 응답만 내리기.

분산 락(Distributed Lock): Redis 등을 이용해 동일한 Transaction ID에 대해 동시에 여러 요청이 들어오더라도 하나만 처리되도록 잠금 장치를 마련.
```
