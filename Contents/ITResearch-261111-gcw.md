
# Node.js 및 npm 보안 취약점 현황과 대응 방안

## 1. 최근 대규모 보안 이슈 발생 원인

- **공급망 공격 증가:** npm 패키지 개발자 계정 탈취 및 정상 패키지에 악성코드를 삽입하는 공격 발생.
- **의존성 구조:** 직접 설치하지 않은 하위 패키지를 통해서도 악성코드가 유입될 가능성 존재.
- **자동 전파:** Shai-Hulud 계열 공격처럼 탈취된 인증정보를 이용하여 다른 패키지까지 감염시키는 사례 발생.
- **AI 해킹 연관성:** 주요 원인은 AI 자체가 아닌 계정 탈취 및 공급망 공격이며, AI는 공격 또는 취약점 탐지에 활용될 수 있는 기술적 요소임.
- **취약점 공개 증가:** 신규 공격뿐 아니라 기존에 존재하던 취약점이 보안 분석 및 조사 과정에서 발견되는 사례도 포함됨.

> **핵심:** Node.js 자체의 보안 취약점과 npm 패키지 공급망 공격은 구분하여 대응해야 함.

## 2. npm 공급망 공격 및 보안 위험

### 2.1 공격 발생 흐름

| 단계 | 동작 및 영향 |
| :--- | :--- |
| **① 패키지 변조** | 공격자가 npm 배포 계정을 탈취하거나 악성 패키지를 배포 |
| ↓ | |
| **② 패키지 설치** | CI/CD 서버에서 npm install 또는 npm ci 수행 |
| ↓ | |
| **③ 악성코드 실행** | 설치 스크립트 또는 빌드 과정에서 악성코드 실행 가능 |
| ↓ | |
| **④ 인증정보 탈취** | GitLab 토큰, SSH 키, 배포 인증정보 등 유출 가능 |
| ↓ | |
| **⑤ 빌드 결과물 변조** | JavaScript Chunk 등에 악성코드 삽입 가능 |
| ↓ | |
| **⑥ 운영 서비스 영향** | 변조된 결과물 배포 시 사용자 브라우저까지 영향 가능 |

※ 공격 유형에 따라 ④~⑥ 단계는 일부만 발생하거나 순서가 달라질 수 있음.

### 2.2 주요 위험 요소

| 구분 | 위험 |
| :--- | :--- |
| CI/CD 서버 | 악성코드 실행 및 서버 침해 |
| 인증정보 | GitLab/Jenkins 토큰, SSH 키 등 탈취 |
| 빌드 결과물 | HTML, CSS, JavaScript Chunk 변조 |
| 운영 서비스 | 악성 JavaScript 배포 및 사용자 피해 |
| Node.js 런타임 | 취약점 종류에 따른 서비스 장애, 인증 우회 등 |

## 3. 현재 서비스 운영 구조 및 영향

### 3.1 React CSR + CI/CD + Nginx 구조

| ① GitLab - 소스코드 관리 |
| :--- |
| - React 소스코드 관리 |
| - package.json 및 잠금 파일 관리 |

↓ **소스 Checkout**

| ② CI/CD 빌드 서버 |
| :--- |
| **Node.js + npm/Yarn 사용** |
| - 의존성 패키지 설치 |
| - React 빌드 수행 |
| - index.html / CSS / JavaScript Chunk 생성 |
| **※ npm 공급망 공격 주요 관리 대상** |

↓ **정적 파일 배포**

| ③ Nginx 운영 서버 |
| :--- |
| - 빌드 결과물만 배포 |
| - HTML / CSS / JavaScript 제공 |
| - Node.js 런타임 미사용 |

↓ **HTTP / HTTPS**

| ④ 사용자 브라우저 |
| :--- |
| - JavaScript Chunk 다운로드 |
| - JavaScript 실행 |
| - React CSR 화면 렌더링 |

### 3.2 현재 환경의 보안 영향

| 구분 | 영향 수준 및 사유 |
| :--- | :--- |
| **CI/CD 서버** | 높음 - npm 패키지 설치 및 Node.js 실행 |
| **Nginx 운영 서버** | 낮음 - Node.js 런타임을 사용하지 않음 |
| **배포 결과물** | 주의 필요 - 빌드 단계에서 악성코드 삽입 가능 |
| **사용자 브라우저** | 주의 필요 - 변조된 JavaScript 실행 가능 |

> **핵심:** 운영 서버에서 Node.js를 사용하지 않더라도 CI/CD 서버를 통한 공급망 공격 위험은 존재함.

## 4. CSR과 SSR의 보안 영향 차이

### 4.1 구조 비교

| 구분 | CSR (현재 환경) | SSR (Node.js 기반) |
| :--- | :--- | :--- |
| 빌드 | CI/CD 서버 | CI/CD 서버 |
| 운영 서버 | Nginx | Node.js 기반 서버 |
| 화면 생성 | 사용자 브라우저 | 서버에서 HTML 생성 |
| Node.js 운영 런타임 | 불필요 | 필요 |
| npm 공급망 공격 | 빌드 환경 영향 | 빌드 및 운영 환경 영향 가능 |
| Node.js 런타임 취약점 | 운영 서버 직접 영향 낮음 | 운영 서버 직접 영향 가능 |
| 주요 관리 대상 | CI/CD 및 정적 파일 | CI/CD 및 운영 런타임 |

### 4.2 핵심 차이

**CSR**
- Node.js는 빌드 단계에서만 사용.
- 운영 서버에서는 정적 파일만 제공.
- CI/CD 의존성 검증과 빌드 결과물 관리가 중요.

**SSR (Node.js 기반)**
- 운영 서버에서 Node.js 런타임 실행.
- 빌드 환경뿐 아니라 운영 런타임 취약점도 관리 필요.
- 서비스 운영 중에도 서버 측 의존성 취약점에 노출될 수 있음.

> **결론:** 현재 CSR 방식은 Node.js 런타임 취약점의 운영 서버 직접 영향이 낮지만, npm 공급망 공격으로부터 완전히 안전한 것은 아님.

## 5. 보안 대응 방안 및 장단점

### 5.1 잠금 파일을 통한 의존성 버전 고정

- **방법:** package-lock.json 또는 yarn.lock 관리.
- **장점**
  - 빌드 환경마다 동일한 의존성 버전 사용 가능.
  - 검증되지 않은 신규 버전의 자동 유입 위험 감소.
  - 의존성 변경 이력 추적 용이.
- **단점 및 한계**
  - 이미 악성코드가 포함된 버전까지 차단하지는 못함.
  - 보안 취약점이 존재하는 기존 버전도 유지될 수 있음.

### 5.2 npm ci 등 잠금 파일 기반 설치

- **방법:** npm 사용 시 npm ci 적용 (Yarn은 버전에 맞는 잠금 파일 검증 옵션 사용).
- **장점**
  - 잠금 파일 기반의 일관된 의존성 설치.
  - 예기치 않은 의존성 버전 변경 방지.
- **단점 및 한계**
  - 악성 패키지 자체를 탐지하거나 차단하지 못함.
  - 설치 과정의 악성 스크립트 실행 가능성은 존재함.

### 5.3 npm audit 및 SCA 취약점 점검

- **방법:** npm audit 및 SCA(Software Composition Analysis) 도구 활용.
- **장점**
  - 알려진 취약점 및 영향받는 패키지 식별.
  - 직접·간접 의존성에 대한 보안 점검 가능.
- **단점 및 한계**
  - 공개되지 않은 취약점이나 신규 악성 패키지는 탐지하지 못할 수 있음.
  - 탐지 결과에 대한 실제 영향도 분석 필요.

### 5.4 npm 설치 스크립트 실행 제한

- **방법:** npm ci --ignore-scripts 등 사용 검토.
- **장점**
  - preinstall, postinstall 등을 통한 악성코드 실행 위험 감소.
- **단점 및 한계**
  - 일부 정상 패키지의 설치 및 빌드가 실패할 수 있음.
  - 빌드 과정에서 실행되는 악성코드까지 모두 차단하지는 못함.

### 5.5 Node.js 보안 버전 관리

- **방법:** 보안 지원 중인 Node.js 버전 사용 및 패치 적용.
- **장점**
  - 알려진 Node.js 런타임 취약점 대응.
  - 빌드 서버의 보안 위험 감소.
- **단점 및 한계**
  - Node.js 업데이트만으로 npm 공급망 공격은 예방 불가.
  - 버전 변경 시 빌드 도구 및 패키지 호환성 검증 필요.

### 5.6 CI/CD 서버 격리 및 접근 통제

- **방법:** 빌드 환경 격리, 외부 통신 제한, 배포 계정 최소 권한 적용.
- **장점**
  - 악성 패키지 실행 시 인증정보 탈취 및 피해 확산 위험 감소.
  - 빌드 서버 침해가 다른 시스템으로 확산되는 위험 완화.
- **단점 및 한계**
  - 허용 네트워크 및 빌드 권한 관리 필요.
  - 기존 CI/CD 구성에 따라 환경 개선 작업 발생.

### 5.7 빌드 결과물 무결성 검증

- **방법:** SHA-256 해시값 비교, 배포 파일 검증 및 이력 관리.
- **장점**
  - 빌드 이후 전송·배포 과정의 파일 변조 여부 확인 가능.
  - 배포 버전 추적 및 롤백 관리에 유리.
- **단점 및 한계**
  - 빌드 단계에서 이미 악성코드가 포함된 경우 해시 비교만으로 탐지 불가.
  - 신뢰 가능한 빌드 결과물 기준 및 검증 절차 필요.

## 6. 현재 환경의 권장 조치 우선순위

| 우선순위 | 조치 항목 | 주요 목적 |
| :--- | :--- | :--- |
| **1** | npm 의존성 및 악성 패키지 점검 | 공급망 공격 탐지 |
| **2** | GitLab/Jenkins 인증정보 보호 | 인증정보 탈취 및 피해 확산 방지 |
| **3** | Node.js 보안 패치 적용 | 빌드 서버 런타임 취약점 대응 |
| **4** | 잠금 파일 기반 의존성 관리 | 의존성 변경 통제 |
| **5** | 빌드 서버 외부 통신 및 권한 제한 | 침해 범위 최소화 |
| **6** | 빌드 결과물 무결성 검증 | 배포 파일 변조 확인 |
| **7** | 설치 스크립트 실행 제한 검토 | 악성 스크립트 실행 위험 감소 |

### 운영 서버 관리

- Node.js가 불필요한 경우 미설치 또는 미실행 상태 유지.
- Nginx 자체 보안 패치 및 접근 권한 관리.
- 검증된 빌드 결과물만 배포.
- 배포 이력 및 롤백 가능한 이전 버전 관리.

※ 폐쇄망 환경에서는 외부 반입 패키지와 사내 npm 저장소의 검증 절차를 추가로 적용해야 함.

## 7. 향후 재발 가능성

- **재발 가능성 높음:** npm 생태계의 복잡한 의존성 및 오픈소스 배포 구조.
- **공격 방식 고도화:** 계정 탈취, 정상 패키지 변조 및 자동 전파 공격 지속 가능.
- **AI 기술 영향:** 취약점 탐지와 공격 자동화 양쪽에 활용될 가능성.
- **단일 조치의 한계:** Node.js 업데이트 또는 잠금 파일 관리만으로 모든 공격 예방 불가.

> **대응 방향:** 일회성 점검보다 의존성 검증, 빌드 서버 보호, 배포 결과물 검증을 지속적으로 수행하는 것이 중요함.

---

## 8. 종합 결론

- 최근 Node.js 관련 보안 이슈는 **런타임 취약점과 npm 공급망 공격을 구분**하여 대응해야 함.
- 현재 **React CSR + 별도 CI/CD + Nginx 정적 파일 배포 구조**는 운영 서버에서 Node.js를 실행하지 않으므로 런타임 취약점의 직접 영향이 낮음.
- 다만 CI/CD 서버에서는 Node.js 및 npm을 사용하므로 악성 패키지에 의한 공급망 공격 위험이 존재함.
- 따라서 **CI/CD 서버의 의존성 검증 및 인증정보 보호를 우선**하고, 빌드 결과물의 무결성 확보를 병행하는 것이 적절함.
