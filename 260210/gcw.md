# Warm-up 현상[재기동 후 API 지연]
---

## ■ 개요

운영 중 롤링 배포(예: 홀수/짝수 서버 교체) 시 재기동된 서버로 트래픽을 받는 순간 다음 현상이 발생할 수 있음:

- 특정 API 응답속도 증가  
- 초기 요청 몰림 시 처리 밀림  
- 일정 시간 후 정상화  

이 현상은 대부분 장애가 아니라 **애플리케이션 Warm-up 과정** 때문입니다.


> 서버는 "기동 완료 상태"와 "최적 성능 상태"가 다르며 일정 요청이 누적되면서 JVM/Spring/Tomcat 내부가 점진적으로 최적화됩니다.

---

# 1. JVM 실행 최적화 (JIT / Hot Method)

## 1.1 핵심 개념

Java는 실행 시 다음 단계를 거칩니다:
<img width="1400" height="950" alt="image" src="https://github.com/user-attachments/assets/23e29132-a311-4ccf-a361-1bfa36c48103" />

1. 바이트코드 인터프리터 실행  
2. 자주 호출되는 코드 감지  
3. JIT 컴파일러가 네이티브 코드 생성  
4. 최적화 코드로 실행  

👉 초기에는 느리고, 반복 실행될수록 빨라질 수 있습니다.

---
### ✔ JIT (Just-In-Time Compiler)
- **의미**: JVM이 실행 중에(런타임에) 자주 실행되는 바이트코드를 **기계어(네이티브 코드)**로 변환해 주는 컴파일러
- **왜 필요한가**: 처음부터 전부 기계어로 컴파일하는 방식(AOT)보다 시작이 빠르고, 실제 실행 패턴에 맞춰 “핫한 부분만” 최적화 가능
- **초기 지연과의 관계**: 재기동 직후에는 아직 변환된 네이티브 코드가 거의 없어서 인터프리터 실행 비중이 높고, 최적화가 덜 된 상태

---

### ✔ Hot Method
- **의미**: JVM이 “자주 호출된다/반복 실행된다”고 판단한 메서드(핫스팟 메서드)
- **왜 중요한가**: Hot Method로 판정되면 JIT가 적극적으로 컴파일/최적화(인라이닝 등)하여 실행속도가 개선
- **초기 지연과의 관계**: 재기동 직후에는 호출 데이터가 없어서 Hot Method 판정이 늦고, 첫 구간에 성능이 낮게 나타날 수 있음

---

### ✔ 코드 최적화 프로파일링 (Code Optimization Profiling)
- **의미**: JVM이 실행 중에 코드 사용 패턴을 수집/학습하는 과정
- **무엇을 수집하나**:
  - 어떤 메서드가 자주 호출되는지(Hot 여부)
  - 조건문이 주로 어느 쪽으로 흐르는지(분기 패턴)
  - 객체 생성이 얼마나 자주 일어나는지(할당 패턴)
- **초기 지연과의 관계**: 초기에는 학습 데이터가 적어서 보수적으로 실행되고, 데이터가 쌓이면서 최적화 폭이 커짐

---

# 2. 클래스 로딩 및 Spring Bean 초기화

## 2.1 발생 원리

Spring Boot 시작 시 보통 다음이 수행됩니다:
<img width="1474" height="753" alt="image" src="https://github.com/user-attachments/assets/914c394a-b5c1-45fb-ab96-41243c28c75e" />

- 클래스 로딩  
- Bean 생성  
- DI(Dependency Injection)  
- AOP Proxy 생성  
- Annotation 스캔  

보통 기동 시 끝나지만, 아래는 **첫 호출 시점까지 지연**될 수 있습니다:

- Lazy Bean 초기화  
- 특정 컴포넌트 첫 호출 시 생성  
- Reflection 기반 처리  

---

### ✔ AOP Proxy
- **의미**: Spring이 트랜잭션/로깅/보안 같은 공통 기능을 적용하기 위해 실제 Bean 대신 “대리 객체(Proxy)”를 만드는 방식
- **호출 흐름 예시**:
  - Controller → Proxy(Service) → 실제 Service
- **초기 지연과의 관계**: Proxy 생성/Advisor(적용 규칙)/Interceptor 준비 등이 초기 또는 첫 호출에 발생할 수 있음

### ✔ Reflection 기반 처리
- **의미**: 런타임에 클래스/메서드/필드 정보를 읽고, 동적으로 호출하는 기능(리플렉션)
- **왜 쓰나**: 애노테이션 기반 DI, 매핑, AOP, 직렬화 등 프레임워크가 “코드를 몰라도” 동작하기 위해 사용
- **초기 지연과의 관계**: 일반 호출보다 느린 편이라, 초기에는 분석이 많이 일어나면 지연이 생길 수 있음

### ✔ Reflection 캐시 생성 / Reflection 결과 캐시
- **의미**: Spring이 리플렉션으로 얻은 결과(메서드 핸들, 애노테이션 파싱 결과 등)를 다시 계산하지 않도록 저장하는 캐시
- **초기 지연과의 관계**: 재기동 후 캐시가 비어 있어 첫 요청에서 리플렉션 비용이 크게 보일 수 있음

# 3. 애플리케이션 내부 캐시 워밍업

## 3.1 대표 캐시 유형

### - Local Cache (Caffeine/Ehcache 등)  
- **의미**: 서버 프로세스 내부 메모리에 저장되는 캐시(재기동 시 사라짐)
- **초기 지연과의 관계**: 첫 조회는 캐시 미스로 느릴 수 있고, 이후는 빠름

### - Metadata Cache
- **의미**: Spring이 애노테이션/Bean 정의/설정 파싱 등 “메타정보”를 저장해두는 캐시
- **초기 지연과의 관계**: 초기 구축 비용이 첫 요청에 섞여 보일 수 있음(특히 Lazy 초기화일 때)

### - Config/Lookup 캐시  
- **의미**: 설정값 조회나 특정 리소스/컴포넌트 검색(lookup) 결과를 저장하는 캐시
- **초기 지연과의 관계**: 첫 조회는 계산/파싱/검색이 필요해 느릴 수 있음

# 4. Thread Pool 및 Executor 워밍업

### ✔ Servlet Thread Pool
- **의미**: Tomcat이 HTTP 요청을 처리하기 위해 운영하는 스레드 풀
- **초기 지연과의 관계**: 재기동 직후엔 최소 스레드 상태일 수 있어, 요청이 몰릴 때 스레드 생성/확장이 따라오며 지연이 발생할 수 있음

### ✔ Async Executor
- **의미**: `@Async`, 비동기 이벤트 처리 등에 쓰는 스레드 풀(별도 Executor)
- **초기 지연과의 관계**: 풀 생성/스레드 확보가 덜 된 상태에서 작업이 몰리면 큐 대기가 생길 수 있음

### ✔ Scheduler Thread
- **의미**: `@Scheduled` 같은 스케줄 작업을 실행하는 스레드(또는 스레드 풀)
- **초기 지연과의 관계**: 재기동 직후 스케줄러 초기화/작업 첫 실행이 겹치면 CPU/스레드 자원 경쟁으로 영향이 날 수 있음

---

# 5. 기타 JVM 내부 웜업 요소 (GC / 메모리 안정화)

### ✔ GC 메모리 상태 안정화
- **의미**: 애플리케이션의 할당/해제 패턴이 안정되며, GC가 “적절한 타이밍/빈도”로 돌아가도록 시스템이 안정화되는 과정
- **초기 지연과의 관계**: 기동 직후엔 객체 생성이 많아 GC 이벤트가 더 자주 보일 수 있음

### ✔ Heap allocation 패턴 안정화
- **의미**: 어떤 객체가 얼마나 자주 생성되고 얼마나 오래 살아남는지(생존/소멸 패턴)가 안정되는 것
- **초기 지연과의 관계**: 초기에는 Bean/캐시/초기 데이터 구축으로 할당이 급증해 일시적으로 메모리 압박/GC가 늘 수 있음

### ✔ Minor GC 빈도 증가
- **의미**: Young 영역에서 발생하는 GC(짧게 사는 객체가 많이 생길 때 잦아짐)
- **초기 지연과의 관계**: 초기화 구간에서 단기 객체 생성이 많으면 Minor GC가 잦아져 지연이 체감될 수 있음

# 6. 실제 운영에서 자주 보이는 패턴

롤링 배포 시 흐름:

서버 재기동 완료  
↓  
트래픽 즉시 인입  
↓  
JIT / 캐시 / Thread Pool 초기 상태  
↓  
응답 지연 발생  
↓  
몇 분 후 정상화  

특히:

- 트래픽이 순간 집중될수록 더 잘 보임  
- 특정 API만 느린 경우가 많음

# 7. 웜업 완화 방법 (실무 팁)

## ✔ 사전 트래픽 워밍업 (가장 효과적)
서버 오픈 전:

- 주요 API 호출  
- 캐시 생성  
- Hot Method 형성 유도(JIT 워밍업)  

## ✔ 트래픽 점진적 전환
가능하면:

0% → 20% → 50% → 100%

# ■ 최종 정리

Spring Boot + Tomcat 재기동 후 API 지연은 주로 다음 때문입니다:

1. JVM JIT 컴파일 최적화 진행(Hot Method 형성 전)  
2. Spring Bean/클래스 초기화(AOP/Reflection 포함)  
3. 애플리케이션 캐시 구축(각종 Cache miss)  
4. Thread Pool/Executor 확장 및 안정화  
5. GC/Heap 패턴 안정화  

👉 DB나 네트워크 문제가 없어도 충분히 발생 가능한 정상 현상입니다.

특히 롤링 배포 시:

> "재기동 서버에 트래픽을 갑자기 몰아줄 때" 가장 크게 체감됩니다.
